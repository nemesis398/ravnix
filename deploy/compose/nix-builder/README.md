# nix-builder: known gaps

The compose project's header in `docker-compose.yaml` says what the builder and the cache are and how to deploy and update them. This file lists what they do not cover. `tests/services/nix-builder.md` records the checks behind each point.

- **The router's public address.** The egress rule drops traffic to private addresses, to the mesh range `100.64.0.0/10` and to the host itself. The router's public address is none of these, and it is the ISP's and changes, so no fixed rule on the host fits it. Probed from inside the builder, the router refused every TCP port it was asked for with an ICMP reject (`No route to host`) and gave no DNS answer over UDP. A port forward or an admin interface on the router's public side would still be reachable from a build. The rule for that belongs on the router.
- **The time between the rule going and the builder stopping.** The builder probes the rule every `NIX_BUILDER_PROBE_INTERVAL` seconds and stops the Nix daemon and sshd after `NIX_BUILDER_PROBE_FAILURES` failed probes in a row: about 30 s with the defaults. A build that runs in that time reaches the LAN until the container restarts, which ends it.
- **What the probes stand for.** They are TCP connection attempts to two targets: the cache's port on the host's own address, which the rule's input chain drops, and `NIX_BUILDER_PROBE_LAN`, which its output chain drops. The rule covers every protocol and address in its ranges, and the probes check only that both chains are in the path. `nix-firewall` connects to the same targets from the host on every pass, and the builder counts a probe only while that control says each answered, at most `NIX_BUILDER_CONTROL_MAX_AGE` seconds ago (30 by default). A target that goes dark therefore closes the gate instead of opening it. What the control cannot see is a target that answers the host but would give the builder no answer even without the rule, such as a port the target's own firewall opens to the host's address alone, and a probe that the builder's CPU starves past its timeout while the host is not starved. A control target inside the builder that must answer, such as `NIX_BUILDER_DNS` on TCP port 53, would cover the second, at the price of closing the gate whenever that resolver or the internet is down; it is not there.
- **The control's own window.** The control is up to `NIX_BUILDER_CONTROL_MAX_AGE` seconds old. A target that goes dark in that time, while the rule is also gone, passes the probe until the control catches up.
- **Two keepers at once.** Two runs of `firewall.sh` at the same time can leave a jump twice. The next pass of the keeper takes the second copy out.
- **Garbage collection.** When the backups bring the store's filesystem under `NIX_MIN_FREE`, every build starts a collection that empties the cache, and `NIX_MAX_FREE` can then never be reached. A limit on the store's own size, kept by a job, would be the real policy.
